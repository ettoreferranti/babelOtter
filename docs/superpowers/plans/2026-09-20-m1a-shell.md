# M1a Shell — Capture, Replacement & the Ollama Client

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete M1a by adding the two halves that touch the outside world — reading and writing a selection in other applications, and streaming from the Ollama daemon over loopback — on top of the pure core delivered by `2026-09-19-m1a-core.md`.

**Architecture:** Every part of this plan is split along one line: the parsing, framing, tier-selection and policy logic is pure and lives in `BabelOtterKit` where CI can prove it; the system calls that cannot run in CI live behind narrow protocols with fake implementations for tests and one real implementation each. The Ollama client is the single file in the package permitted to reference networking APIs, and it routes exclusively through `OllamaEndpoint`.

**Tech Stack:** Swift 6, swift-testing, `ApplicationServices` / `AXUIElement`, `AppKit` (shell target only), `URLSession` with `bytes(for:)` for NDJSON streaming. No third-party dependencies.

**Spec:** `docs/superpowers/specs/2026-09-18-babelotter-design.md`.
**Measured reality:** `docs/architecture.md` §7 — written from spike #30, run against real applications on macOS 27. **§7 supersedes §2–3 where they disagree, and this plan is built on §7, not on the original two-tier model.**

## Global Constraints

- **NFR-P4 — one networking call site.** `Config/networking-allowlist.txt` permits exactly `Sources/BabelOtterKit/LLM/OllamaClient.swift`. `NetworkingCallSiteTests` fails the build on a second one. The guard matches on **spelling and does not exempt comments**, so avoid writing the flagged spellings even in prose (the core plan hit this twice).
- **NFR-P2 — loopback only.** Every request is built from an `OllamaEndpoint`, which makes a non-loopback host unrepresentable.
- **NFR-Q3 — the core imports no UI framework.** `AppKit`, `SwiftUI`, `UIKit`, `Cocoa`, `Carbon` are banned inside `BabelOtterKit`. Anything needing them lives in `Sources/BabelOtterApp`. `ApplicationServices` is **not** banned, so the AX calls themselves may live in the kit; `NSPasteboard` and `NSRunningApplication` may not.
- **Mutation score ≥ 80%.** Every new file under `Sources/BabelOtterKit` must be assigned to a mutation pass in `.github/workflows/ci.yml` or CI fails by design.
- **Avoid two muter parse bugs** (both poison a whole file, because mutant schemata compile every mutant into one binary): a `while` condition that is a comma-conjunction containing a relational operator, and a ternary whose condition ends in an enum member. Write nested `guard`s and `if`/`else` instead. See `muter.conf.yml` and the note in `PromptBuilder.languages`.
- **Verify guards by making them fail.** Every invariant below gets a planted defect and an observed failure before it is believed.

## What spike #30 measured, and what it obliges this plan to do

These are not background reading. Each one changes a design decision below.

1. **Capture is three tiers, not two.** `kAXSelectedTextAttribute`, then WebKit's parameterized `AXSelectedTextMarkerRange` → `AXStringForTextMarkerRange`, then the clipboard. Safari and Mail return `noValue` for tier 1 and expose the selection only through text markers. Skipping tier 2 makes Safari and Mail clipboard-only — less private and less reliable than they need to be.
2. **`AXUIElementSetAttributeValue` lies**, and that is why there is no Accessibility write path at all. Measured across four web surfaces: each returns `.success` and changes nothing, including an editable `<textarea>` that reads perfectly. **Replacement is always the clipboard** (Tasks 9, 10).
3. **Attribute presence is not capability.** VS Code advertises `AXSelectedText`, `AXSelectedTextRange`, `AXSelectedTextRanges` *and* `AXSelectedTextMarkerRange`, and returns empty from all of them. **Capability detection must attempt a real capture and require a non-empty result** (Task 8). Probing attribute names classifies VS Code as tier 1; it is tier 3.
4. **`AXManualAccessibility` does not help.** It returns `attributeUnsupported` on Outlook and Teams, and VS Code stayed unreadable. Arming Electron trees was a planned task and has been dropped: those apps go through the clipboard, which is measured to work there.
5. **The clipboard is the conduit, by decision.** It is the only capture path for Electron and the only replacement path anywhere. `NFR-P10` makes restoring it a privacy mechanism rather than a courtesy, because Universal Clipboard transfers at paste time (Task 10).

### Task 1: NDJSON framing across packet boundaries (#41)

**Files:**
- Create: `Sources/BabelOtterKit/LLM/NDJSONFramer.swift`
- Test: `Tests/BabelOtterKitTests/LLM/NDJSONFramerTests.swift`

**Interfaces:**
- Produces: `struct NDJSONFramer: Sendable { mutating func consume(_ chunk: String) -> [String]; mutating func finish() -> [String] }`

**Design notes:**

Pure and CI-testable, which is the point of separating it from the client: #41's acceptance criterion "a partial line split across packets is buffered and parsed correctly once complete" is a framing property, not a networking one, and deserves a test that does not need a daemon.

`consume` returns only **complete** lines and retains the trailing partial in a buffer. `finish` returns whatever remains, so a final line without a newline is not silently dropped — the failure mode where the last token of a generation disappears.

Empty lines are skipped rather than returned: Ollama's NDJSON contains them, and returning them would push the "is this malformed?" decision onto every caller.

- [x] **Step 1: Write the failing tests**

```swift
import Testing
@testable import BabelOtterKit

@Suite("NDJSON framing survives packet boundaries")
struct NDJSONFramerTests {

    @Test("a whole line in one chunk is returned")
    func wholeLine() {
        var framer = NDJSONFramer()
        #expect(framer.consume("{\"a\":1}\n") == ["{\"a\":1}"])
    }

    @Test("a line split across two chunks is buffered until complete")
    func splitLine() {
        var framer = NDJSONFramer()
        #expect(framer.consume("{\"a\":") == [])
        #expect(framer.consume("1}\n") == ["{\"a\":1}"])
    }

    @Test("a line split across three chunks still arrives once")
    func splitAcrossThree() {
        var framer = NDJSONFramer()
        #expect(framer.consume("{\"a") == [])
        #expect(framer.consume("\":") == [])
        #expect(framer.consume("1}\n") == ["{\"a\":1}"])
    }

    @Test("several lines in one chunk all come back, in order")
    func severalLines() {
        var framer = NDJSONFramer()
        #expect(framer.consume("{\"a\":1}\n{\"b\":2}\n") == ["{\"a\":1}", "{\"b\":2}"])
    }

    @Test("a trailing partial is kept, not emitted")
    func trailingPartialHeld() {
        var framer = NDJSONFramer()
        #expect(framer.consume("{\"a\":1}\n{\"b\"") == ["{\"a\":1}"])
    }

    @Test("finish returns the last line when the stream ends without a newline")
    func finishFlushes() {
        var framer = NDJSONFramer()
        _ = framer.consume("{\"a\":1}")
        #expect(framer.finish() == ["{\"a\":1}"])
    }

    @Test("finish on an empty buffer returns nothing")
    func finishEmpty() {
        var framer = NDJSONFramer()
        #expect(framer.finish() == [])
    }

    @Test("blank lines are skipped rather than surfaced as malformed")
    func blankLinesSkipped() {
        var framer = NDJSONFramer()
        #expect(framer.consume("{\"a\":1}\n\n{\"b\":2}\n") == ["{\"a\":1}", "{\"b\":2}"])
    }

    @Test("CRLF line endings frame correctly")
    func crlf() {
        var framer = NDJSONFramer()
        #expect(framer.consume("{\"a\":1}\r\n") == ["{\"a\":1}"])
    }
}
```

### Task 8: Tier selection by attempted capture, not by attribute probing (#31)

**Interfaces:**
- Produces:

  - `protocol SelectionSource: Sendable { func read(tier: CaptureTier) -> String? }`

**Design notes:**

**This is the task spike #30 called its most misleading result.** VS Code advertises every selection attribute and returns empty from all of them. So the ladder's rule is: try a tier, and accept it **only if it returns a non-empty string**. Never ask what a tier supports.

### Task 9: Replacement, always through the clipboard (#33)

**Files:**
- Create: `Sources/BabelOtterApp/ClipboardReplacer.swift`
- Create: `Sources/BabelOtterKit/Capture/ReplacementOutcome.swift`
- Test: `Tests/BabelOtterKitTests/Capture/ReplacementOutcomeTests.swift`

**Interfaces:**
- Produces:
  - `enum ReplacementOutcome: Sendable, Equatable { case replaced; case failed(reason: String); case notAttempted(reason: String) }`
  - `protocol PasteboardWriting: Sendable` — save, write, restore, `changeCount`
  - `struct ClipboardReplacer` — re-activate the source app, write, synthesise Command-V, restore

**Design notes:**

**There is no Accessibility write path, by decision (2026-09-20).** Measurement
killed it: every web surface accepts `AXUIElementSetAttributeValue`, returns
`.success`, and changes nothing — including a plain editable `<textarea>` in
Safari that reads 129 characters cleanly. AX write is confirmed working only in
native AppKit text.

Keeping it would have bought TextEdit and Preview, and cost a second tier
ladder evaluated per direction, a read-back-and-compare verifier that exists
solely because the API lies, and a whole class of "told the user Replaced over
untouched text" defects — which is exactly what #34 exists to prevent. One
mechanism for replacement is both simpler and more honest about what was
measured.

So: **capture uses the Accessibility ladder; replacement always uses the
clipboard.** The asymmetry is the design, not an inconsistency.

`notAttempted` is distinct from `failed` because they need different messages:
"the source application has gone" is not "the paste did not land".

### Task 10: Clipboard capture and replacement mechanics (#32, #33)

**Files:**
- Create: `Sources/BabelOtterApp/ClipboardCapture.swift`
- Create: `Sources/BabelOtterKit/Capture/ClipboardPolicy.swift`
- Test: `Tests/BabelOtterKitTests/Capture/ClipboardPolicyTests.swift`

**Design notes:**

`NSPasteboard` and synthetic key events need `AppKit`, so the mechanics live in
the app target; `NoUIImportsTests` enforces that. The *policy* is pure and lives
in the kit, where CI can prove it.

Measured 2026-09-20 with `Tools/clipboard-probe.sh`, and these are requirements
rather than observations:

1. **`changeCount` is the only signal a capture worked.** An unmoved count must
   be treated as failure. The probe's first version read the pasteboard
   regardless and pasted 36 characters of unrelated older clipboard content into
   a live Mail message. A real implementation with that bug corrupts a document
   with text from a previous copy.
2. **Retry once, with a longer window.** Three of seven captures produced
   nothing on the first attempt. Whether that was empty selections or timing is
   unresolved, and a single retry costs nothing and distinguishes them in the
   logs.
3. **Save and restore every type of every item**, not just the string. A tool
   that clobbers the clipboard while claiming to protect it is worse than one
   that does not try.
4. **Restore on every path, including failures** (`NFR-P10`). Universal
   Clipboard transfers at paste time rather than at copy time, so the restore is
   what ends the exposure. This is a privacy mechanism, not a courtesy, and the
   failure paths are where it will be forgotten.

- [x] **Step 1: Write the failing tests** — the previous contents are restored after a successful capture; after a capture that times out; after the read throws; the restore happens after the read, never before (ordering fake); an unmoved `changeCount` is reported as failure rather than returning stale contents; exactly one retry is issued; a capture reports `tier == .clipboard` so the UI can say so.
- [x] **Step 2–4: fail, implement, pass.**
- [x] **Step 5: Plant the defect that shipped in the probe** — read the pasteboard without checking `changeCount`. The stale-contents test must fail. Revert.
- [x] **Step 6: Add to the mutation list and commit.**

### Task 11: Capture-only strict mode (#77, rewritten)

**Files:**
- Create: `Sources/BabelOtterKit/Capture/CapturePolicy.swift`
- Modify: `Sources/BabelOtterKit/Config/Configuration.swift` — add `strictCaptureOnly: Bool`
- Test: `Tests/BabelOtterKitTests/Capture/CapturePolicyTests.swift`

**Design notes:**

**#77 as originally written is no longer buildable.** "Strict
Accessibility-only mode" assumed the clipboard was an avoidable fallback. With
replacement now always going through the clipboard, strict AX-only would mean
"can read in Safari, Mail and Outlook, can replace nowhere" — not a product.

What the measurements *do* permit is a **capture-only** strict mode: refuse the
clipboard for reading, accept it for writing. That is coherent, and it is worth
having, because the asymmetry in exposure is real. Reading puts the user's
*existing* text — an email they received, a document they did not write — on the
pasteboard. Writing puts babelOtter's own output there, which the user has just
seen and approved.

In strict mode the ladder may attempt tiers 1 and 2 only, and an app where
neither works reports **"this application cannot be read without the
clipboard"** — a refusal the user can act on, distinct from an empty selection
(#35), because the two need different messages.

`strictCaptureOnly` defaults to `false`. Making it the default is a product
decision, and the per-application table in `docs/architecture.md` section 7 is
what it should be decided against: strict capture-only means no capture at all
in Teams, Word, OneNote or VS Code.

- [x] **Step 1: Write the failing tests** — default configuration allows all three tiers; strict mode allows exactly tiers 1 and 2; strict mode with no AX tier available yields an explicit refusal naming the application; the refusal is distinguishable from an empty selection; replacement is unaffected by the setting.
